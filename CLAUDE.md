## Architecture

**Data flow is fixture-first by deliberate design, not a shortcut:**

- `src/data/activities.json` — the committed fixture `lib/data.js` actually reads: 14 small, hand-written synthetic activities covering all activity types plus some `null` HR/calories fields. Deterministic and safe to publish.
- `src/data/activities.local.json` — **gitignored, not committed.** A one-time snapshot of 100 real activities pulled via the `garmin` MCP server, kept at a different filename on purpose so a local swap can't accidentally get committed as a change to the tracked fixture path. Optional richer dataset for local dev only — don't point `lib/data.js` at it in a commit. See `PLAN.md`'s Data strategy for the full reasoning and the name-genericization rule applied to it.
- `src/data/wellness.json` / `.local.json` — added 2026-07-29, same real-local/synthetic-committed pattern as `activities.json`. One record per day: sleep score, resting/avg/max heart rate, avg/max stress, body battery charged/drained, training readiness score, training status label, VO2 max. Real data (`.local.json`) covers 2026-07-15..2026-07-21 only (7 days) — the underlying Garmin endpoints for sleep/HR/stress/training-readiness/training-status are all per-day-only (no date-range param), so a wider window means proportionally more MCP calls.
- `src/data/vo2MaxTrend.json` / `.local.json` — added 2026-07-29. Sparser, longer-range VO2 max trend (real: 8 points spanning 2026-05-01..2026-07-21) — deliberately separate from `wellness.json`'s daily `vo2Max` field, since VO2 max updates gradually and a multi-month view is the more meaningful one; this endpoint does take a date range directly.
- `src/data/weighIns.json` / `.local.json` — added 2026-07-29. Date + weight in kg; real data has 25 measurements. Also takes a date range directly.
- `src/data/golfRounds.json` / `.local.json` — added 2026-08-05. **A round comes in one of two fidelities** (mixed-fidelity support added 2026-08-05 after the Golf Pad research below):
  - **Hole-by-hole** — `date`/`course`/`tees` plus a `holes` array of `{hole, par, score, putts, fairway, gir, penalties}`. Hand-entered.
  - **Summary-only** — `date`/`course`/`tees`/`source` plus a `summary` of round totals (`holesPlayed`, `score`, `par`, `putts`, `girCount`, `fairwaysHit`, `fairwayAttempts`, `penalties`, `sandShots`, `courseRating`, `slope`). This is everything Golf Pad's free-tier CSV export can express. `courseRating`/`slope` are carried but unused — they'd make a real WHS handicap differential computable later.
  - The committed fixture holds **6 hole-by-hole rounds plus 1 summary-only round (2026-08-02)** on purpose, so the degradation path is exercised by e2e rather than only by unit tests. Because the picker defaults to the most recent round, **the golf view opens on the summary-only round** — the degraded state is the default, which is why `smoke.spec.js` asserts `87` and a trend chart rather than a scorecard.
  - **Hand-entered, never synced** — the `garmin` MCP server exposes no golf endpoints (Garmin Golf is a separate product API), so `scripts/sync_garmin.py` doesn't touch this dataset and shouldn't be extended to try. **Golf Pad has no API either** (researched 2026-08-05 — see `scripts/import_golfpad.py`'s docstring and PLAN.md); its CSV export is the only supported route in, and it is manual, so this dataset can never be on a schedule the way the Garmin one is. Committed fixture is 6 synthetic rounds across 2 courses (one 9-hole round, one eagle, two birdies, two holes with `putts: null` to exercise the not-recorded path). **Two field conventions the math depends on:** `fairway` is `null` on par 3s (no fairway to hit — must not count as a miss), and `putts` is `null` when not recorded (excluded from putting stats rather than counted as zero). Note the `.gitignore`'s `*.local` glob does *not* match `*.local.json`, so each real dataset is listed by name — `golfRounds.local.json` needed its own line.
- `src/lib/data.js` — the *only* module allowed to read any fixture. Components never import a fixture JSON file directly. `getActivities()`/`getWellness()`/`getVo2MaxTrend()`/`getWeighIns()` all follow the same shape. **Updated 2026-08-01:** each function can source from a dataset's `.local.json` file via `import.meta.glob('../data/*.local.json', { eager: true })` instead of the committed synthetic fixture — but only when `VITE_USE_LOCAL_DATA=true` is set (`VITE_USE_LOCAL_DATA=true npm run dev` to preview real data). **Deliberately not presence-based**, despite that being the original design: `scripts/sync_garmin.py` runs on a launchd schedule, so `.local.json` files can appear in the background without the dev running the sync themselves that session — presence-based switching meant `npm run test:e2e`/`test:e2e:smoke` silently rendered real Garmin data and failed the fixture-pinned assertions in `e2e/smoke.spec.js` the moment a scheduled sync landed, for reasons unrelated to any code change (caught and fixed 2026-08-01). `import.meta.glob` still resolves whatever `.local.json` files exist at build time regardless of the flag, so a fresh clone/CI with none present still builds cleanly either way.
- `scripts/import_golfpad.py` — added 2026-08-05. Imports a Golf Pad CSV export into `src/data/golfRounds.local.json`. `uv run` script with PEP 723 inline deps like `sync_garmin.py`, but **stdlib only** — no dependencies. Two things to know before touching it:
  - **No SQLite, unlike `sync_garmin.py`, and that's deliberate** (the docstring says so, so the inconsistency reads as a decision): that script pulls incremental trailing windows and needs a cumulative store or history falls off the back; this export is a full dump of every round every time, so there's nothing to accumulate and the JSON file *is* the store.
  - **The merge must never downgrade a hand-entered round.** Keyed on `(date, course)`: a round already carrying `holes` keeps them and only has its `summary` refreshed. Losing hand-typed holes would be unrecoverable — no free-tier export can regenerate them. This is the behaviour to re-check after any edit to `merge()`.
  - Headers are undocumented and have varied between app versions, so `FIELD_ALIASES` accepts several spellings per field against normalised headers, and a missing **required** column aborts the run printing every header actually seen. Add new spellings there rather than loosening the check. `--dry-run` prints the parse and merge plan and writes nothing.
- `scripts/sync_garmin.py` — added 2026-08-01, self-contained `uv run` script (PEP 723 inline deps: `garminconnect`, no separate venv/`pyproject.toml`). Pulls a trailing window from Garmin (14 days activities/wellness, 90 days VO2 max/weigh-ins), upserts into `scripts/garmin.local.db` (SQLite, gitignored) by natural key, then materializes the accumulated view back out to `src/data/*.local.json`. Reuses the same `~/.garminconnect` token cache as the `garmin` MCP server — no new credentials. Scheduled daily at 7am via macOS launchd — **loaded and active as of 2026-08-04** (`~/Library/LaunchAgents/com.alexbrewster.fitness-dashboard-sync.plist`, installed from `scripts/launchd/`; see that directory's README for status/uninstall commands). This is local-only tooling; it never runs in CI and the app never talks to SQLite directly.
- `src/lib/golf.js` — added 2026-08-05. Pure functions only, same discipline as `stats.js` but a **separate module on purpose**: `stats.js` is activity/wellness math over Garmin data, golf is hole-by-hole scorecards, and the two share no inputs. Exports `getRoundSummary`, `getScoreDistribution`, `getScoringByPar`, `getPuttingStats`, `getScoringTrend`, `getHoleAverages`, `getNineSplit`. Three decisions an interviewer will probe, all documented in the file's header comment:
  - **Scrambling** is counted as "missed the green in regulation, still made par or better" — the standard proxy when you only have hole-by-hole data. It is *not* real up-and-down tracking, which needs to know where each shot finished. Say so rather than claiming it's the same stat.
  - **No Strokes Gained, deliberately.** SG needs every shot's starting lie and distance-to-hole against a baseline table; hole-by-hole scorecards cannot produce it. A number labelled "strokes gained" that wasn't computed that way would be worse than not having one.
  - **`puttsPerRound` is normalised to 18 holes** (per-hole average × 18) rather than divided by round count — otherwise the 9-hole round and the two `putts: null` holes drag the average down for reasons unrelated to putting.
  - `getHoleAverages(rounds, course)` takes a course argument because averaging "hole 7" across two different courses describes nothing. Percentages return `null` (not `0`) when the denominator is zero, so the UI can render an em dash instead of a misleading 0%.
  - **`hasHoleData(round)` (added 2026-08-05) is the one predicate for "is this round hole-by-hole?"** — used by `golf.js`, `Scorecard.jsx`, `RoundPicker.jsx`, and `App.jsx`, so the question is answered in exactly one place. The supporting rules: `getRoundSummary` branches on it and returns **`null` (not `0`) for `onePutts`/`threePutts`/`scramblingPct`** on a summary-only round — those are unknowable without per-hole rows, and `GolfSummary.jsx`'s existing `formatPct` already renders `null` as an em dash, so the KPI row needed no change. The private `allHoles` does `round.holes ?? []`, which is the single line that makes every per-hole aggregate skip summary-only rounds instead of throwing. `getNineSplit` returns `null` outright for them. `getScoringTrend` works on both shapes — it's the panel that keeps working on imported data, which is the whole point of the second shape.
- `src/lib/stats.js` — pure functions only (totals, weekly rollup, filters), deliberately separate from React components so the math is testable without rendering anything.
  - `getTotals`'s `streak` field is the **longest run of consecutive calendar days with an activity in the given list** — not "current streak as of today." A "today"-relative streak would make assertions against the static fixture depend on the system clock, breaking the project's deterministic-testing design. Computed via a private `getDateKey`/`getStreak` pair (same file-private-helper pattern as `getWeekStart`); `getDateKey` uses local `getFullYear`/`getMonth`/`getDate` rather than `toISOString()`, deliberately avoiding the UTC day-shift risk that method carries in timezones ahead of UTC (see `getWeekStart`, which does use `toISOString()` — not fixed, since it works for the existing tests, but don't copy that pattern into new code).
  - `getActivityTypeBreakdown(activities)` — added 2026-07-29. Counts per activity `type`, sorted most-common-first. No new fixture needed — every activity already has a `type` field. Feeds `ActivityTypeBreakdown.jsx`.
  - `groupByWeek(activities)` — added 2026-07-31 (visual-redesign Phase 3), private. Buckets activities into `Map<weekStart, activity[]>` using the same `getWeekStart` as before; `getWeeklyDistance`/`getWeeklyDuration`/`getWeeklyActivityCount` are now thin reducers over the same groups (sum `distanceMeters`, sum `durationSeconds`, count, respectively) instead of each re-implementing the bucketing — a refactor extracted while adding the latter two, covered by a consistency test asserting all three produce identical `weekStart` keys for the same input.
- `src/components/Summary.jsx` — presentational only: takes `totals` (from `getTotals()`) plus `weeklyDistance`/`weeklyDuration`/`weeklyActivityCount` (the three `getWeekly*` arrays) and formats/renders them as icon + value + sparkline tiles (added 2026-07-31). **Restructured 2026-08-05:** a local `Stat` sub-component replaces four near-identical hand-written blocks, and each formatter now returns `{value, unit}` so the unit can be demoted visually beside an oversized numeral. **The `data-testid` moved onto the numeral alone** — `total-distance` is now `73.6`, not `73.6 km`, and `streak` is `3`, not `3 days`. Both e2e specs were updated, and both gained a `.summary-unit` assertion so demoting the unit visually didn't silently drop it (including the singular "day" case, which `formatStreak` still branches on). Doesn't call any `lib/` function itself — `App.jsx` computes everything and passes it down, keeping the component testable with fake props later without needing the fixture. Each stat's value span has a `data-testid` (`total-distance`, `total-duration`, `activity-count`, `streak`) — use those in Playwright, not positional selectors like `.summary-value:last-child`, which silently points at the wrong stat if another one gets added later (happened here when `streak` was added as a 4th stat). The streak tile deliberately has no sparkline — there's no natural weekly series for "longest run of consecutive days" without inventing one, which would contradict why `streak` itself is defined the way it is (see above).

Presentational, takes a `values` array and renders a small hand-rolled SVG trend line (computed points, not Recharts — there's no axis/tooltip/legend need for an inline tile decoration this small). `aria-hidden="true"`: it's a supplementary trend indicator sitting next to a tile whose text value already carries the number a screen reader needs, not an independent data surface.

Returns Monday-start `{start, end}` `'YYYY-MM-DD'` bounds for the week containing `referenceDate`. Deliberately uses `getDateKey`'s local-date math (`getFullYear`/`getMonth`/`getDate`), not `toISOString()`, unlike `getWeekStart` above — this is a case where the UTC-day-shift risk actually matters (a "this week" button that's off by a day near midnight would be an obviously wrong, user-visible bug), so the fix wasn't skipped here the way it was left alone in `getWeekStart`. Takes an explicit `referenceDate` param specifically so its own tests don't depend on the system clock; `e2e/filters.spec.js`'s "This week" test mirrors the same local-date math independently (computed from the real `Date.now()` at test time) rather than importing the function, since e2e specs assert against the rendered app, not the module directly.
- `src/components/ActivityTypeBreakdown.jsx` — added 2026-07-30 as a horizontal Recharts `BarChart`; changed to a Recharts `Pie`/donut 2026-07-31 (visual-redesign Phase 4). Presentational, takes a `breakdown` prop (`getActivityTypeBreakdown()`'s output). **Color assignment is a fixed `type → CSS-variable` lookup (`COLOR_BY_TYPE`), not derived from the slice's position in the (count-sorted) `breakdown` array.** This matters: the slices themselves are correctly re-ordered by count when the data changes (e.g. via the date filter), but if color also came from array position, the same activity type could silently repaint a different color between renders.   - `.page-section`'s top margin/border and its `:first-of-type` reset went away in the same change: they existed to separate stacked sections, and there are no longer stacked sections to separate.
- **Visual restyle, 2026-08-05 (dark-first, oversized numerics).** Near-black canvas, one high-energy accent reserved for progress and data marks, oversized tabular numerals, hairlines instead of card borders, left-aligned content (it was centred, which was a large part of why it read as templated). Points worth knowing:
  - **The `--series-*` palette was re-validated, not replaced.** Moving the canvas invalidates any prior contrast result, so `validate_palette.js` was re-run against the new surfaces: dark passes every check unchanged; light still has slots 3/4/5 below 3:1, the same pre-existing condition mitigated by the direct legend labels. **No palette values changed** — if you move the surfaces again, re-run it again rather than assuming.
  - `--accent` stepped from `#35b8cc` to `#3fd5e8` for the darker canvas (11.09:1), light step from `#0e7c90` to `#0b6e80` (5.56:1). Deliberately *not* the acid-green or vermilion that dark dashboards default to — the cyan is the identity this project already had.
  - **No webfont**, on purpose: this project's thesis is deterministic, screenshot-able testing, and a downloaded face adds a network dependency plus a flash of fallback text that would make the visual-regression stretch goal flakier. Character comes from size, `tabular-nums`, and tracking.
  - New token groups in `index.css`: `--surface-0/1/2` + `--hairline` (three depth steps, no drop shadows), a type scale (`--fs-metric` etc.), and a spacing scale (`--space-1..5`). `--fs-metric` is capped at `3rem` **because above that the widest metric ("10h 7m") stops fitting four-across and the cluster breaks 3+1**, which reads as a bug rather than a deliberate row.
  - **Recharts' grid, axes, and tooltip are restyled in CSS** (`.recharts-cartesian-grid line`, `.recharts-cartesian-axis-*`, `.recharts-default-tooltip`) rather than via per-chart props, so a new chart inherits the recessive treatment instead of having to remember it. The tooltip needs `!important` — Recharts sets its surface as an inline style and exposes no prop for it.
  - `.summary-stat::before` (not `::after`) draws the accent tick: a flex column places `::after` last, which would drop the tick below the sparkline instead of crowning the tile.
  - **The ~390px dark-mode-toggle rough edge is fixed** — `.sidebar-foot` is `position: sticky; right: 0` in the mobile nav, so the toggle stays reachable while the nav scrolls beneath it. `PLAN.md`'s known-rough-edge entry can come off the list.
- `src/index.css` — theming is `prefers-color-scheme`-driven as before, *plus* two `:root[data-theme="dark"]`/`:root[data-theme="light"]` blocks that let the sidebar's toggle override the OS preference in either direction. These only need to repeat the properties that actually differ between modes (`color`, `background-color`, `--series-*`, `--text-secondary`, `--accent`) — an attribute-selector rule like `:root[data-theme]` outranks the plain `:root` specificity of both the default block and the `prefers-color-scheme` block regardless of source order, so nothing else needs touching. `--status-*` and the new `--sidebar-*` tokens (`--sidebar-bg`/`--sidebar-ink`/`--sidebar-ink-muted`/`--sidebar-active-bg`) are declared once, unthemed, on purpose — the sidebar is deliberately always-dark regardless of the app's own light/dark theme (a persistent-chrome pattern, not an oversight).
  - **Gotcha found here:** a CSS comment containing the substring `--status-*/--sidebar-*` (written with no space around the `/`) literally contains `*/` and silently truncates the stylesheet mid-parse during minification — `npm run build` reports success even though the rest of the file, including that `data-theme` override block, vanishes from the production output. Caught by grepping the actual built CSS (`dist/assets/*.css`) for the expected selector, not by trusting a green build. Avoid `*/`-shaped substrings inside any CSS comment, even split across two token names.
- `e2e/smoke.spec.js` — Playwright, tagged `@smoke` via the `{ tag: '@smoke' }` test option, 10 tests. **Updated 2026-08-05 for view switching:** a `goToView(page, name)` helper clicks the sidebar button before asserting, since anything outside the default Activity view is unmounted rather than off-screen. Earlier count was 7 (one added 2026-07-30: the disabled "Reports" nav item is visible/disabled/shows "Soon", via `getByRole('button', {name: /reports/i})` — not a `data-testid`, since there's no dynamic value to protect against `getByText` collisions here, just a static label). Asserts against the exact values the committed synthetic fixture produces (e.g. "73.6 km", "3 days" streak, "61"/"Good"/"Maintaining" training readiness) via `page.getByTestId(...)` — coupled to `activities.json`/`wellness.json`/etc. on purpose, consistent with the project's fixture-first/deterministic-testing design. If a fixture changes, these assertions need updating too.
  - **Updated 2026-07-31 (visual-redesign Phase 4):** the activity-type test now asserts `.chart-activity-types .recharts-pie-sector` count = 7 (was `.recharts-bar-rectangle`, before `ActivityTypeBreakdown.jsx` switched from a bar chart to a donut) plus `getByTestId('activity-type-row')` count = 7 as a second, chart-implementation-agnostic check against the legend.
  - **Gotcha found 2026-07-30:** `.recharts-line-dots circle` used to uniquely identify the weekly-distance chart's dots, back when it was the only line chart on the page. Adding `Vo2MaxChart`/`WeightChart` broke that — the selector now matches all three charts' dots combined. - `e2e/filters.spec.js` — Playwright, untagged (full suite only, not CI's `@smoke` run). Covers the date-range filter interaction: narrows to one week, clearing restores all 14, a no-match range zeroes out the summary and shows 0 chart dots, a partial (one-sided) range leaves activities unfiltered, and a single-day range narrows to exactly that day's one activity.   - **Gotcha found here (now fixed via `data-testid`, see `Summary.jsx` above):** don't assert summary numbers via a page-wide `page.getByText(...)`. ## Test strategy

- **Unit (Vitest, 83 tests):** 40 of them cover `golf.js` (added 2026-08-05) — round summaries, the par-3 `fairway: null` exclusion, scrambling, `putts: null` handling, score distribution, scoring by par, putting rates (including four-putts counting toward the three-putt rate), unsorted trend input, per-hole averages scoped by course, and the 9-hole nine-split. **These build their own small rounds rather than importing `golfRounds.json`** — a fixture edit shouldn't quietly change what a unit test asserts; fixture coupling belongs in the e2e suite. Plus 35 pure-function tests covering all of `stats.js` — totals, weekly bucketing (distance/duration/activity-count, plus a cross-function consistency check), filter subsets, streak (longest-run logic, same-day dedup, unsorted input), activity-type breakdown, `getCurrentWeekRange` (mid-week/Monday/Sunday/year-boundary reference dates, added 2026-08-04), edge cases (empty data, single activity, missing fields) — plus 7 `@testing-library/react` tests: `ScoreRing.test.jsx` (2, added 2026-07-31) verifying the ring's arc math (`stroke-dasharray` proportional to `score/max`) and clamping, and `Scorecard.test.jsx` (6, added 2026-08-05) covering the marker classes, the spoken result text, the omitted back nine on a 9-hole round, the dash for unrecorded putts, and the `PanelUnavailable` fallback for a summary-only round. Component tests needing a DOM use the per-file `// @vitest-environment jsdom` pragma rather than a global environment switch, so `stats.test.js` and `golf.test.js` keep running under the faster default `node` environment.
  - **Gotcha found writing `Scorecard.test.jsx`:** `@testing-library/react`'s auto-cleanup only runs when Vitest's `globals` option is enabled, and it isn't in this repo. Without an explicit `afterEach(cleanup)` the previous test's DOM is still mounted and every `getByText` finds two matches ("Found multiple elements with the text: Out"). Any new component test with more than one `render()` needs that line.
- **E2E (Playwright):** two tiers via tags. `@smoke` (`e2e/smoke.spec.js`: loads, view switching, summary renders, weekly chart, activity-type breakdown, wellness summary, trend charts, disabled "Reports" placeholder, Golf view reachable, date filter scoped to Activity — 10 tests) runs on every push in CI. The full set adds `e2e/filters.spec.js` (7 tests: basic filter, clear, empty-range/no-match, partial-range, single-day, plus two added 2026-08-04 for the Lifetime/This week presets — the latter computes its own expected Monday..Sunday bounds from the real clock rather than asserting a fixed date, since it isn't fixture-pinned like the rest of the file) — runs on demand only (`npm run test:e2e`), not in CI yet — plus `e2e/golf.spec.js` (8 tests, added 2026-08-05: default KPI row, 18-hole scorecard, the 9-hole round dropping its back nine, switching rounds, the eagle marker + its spoken name, the three aggregate charts scoped to their own wrappers, the putting panel, and narrowing the round window). **26 e2e total.** `filters.spec.js` needed no changes for the view restructure: it only ever exercised the Activity view, which is the default.
  - **Gotcha found while building the chart (Milestone 5), applied in the smoke test:** Recharts animates the line being drawn in on mount (~1.5s default). A screenshot/assertion taken too early sees only a partial path — looks exactly like a rendering bug (points 2+ appear disconnected) but isn't. The "chart renders" smoke test asserts `.recharts-line-dots circle` count instead of the line path, since dots are placed at final position immediately rather than animating in.
- **CI (GitHub Actions, `.github/workflows/ci.yml`, added milestone 4 deliberately early):** `npm ci` → `npm run lint` → `npm test` → `npm run build` → install Playwright's chromium → `npm run test:e2e:smoke` → upload the HTML report as an artifact (`if: always()`, so it uploads even on failure), on push/PR to `main`. Runs on Node 20 in the runner (not the local Node v21.6.1 — sidesteps the `styleText`/`rolldown` gotcha below entirely, though `vitest` is pinned regardless). Confirmed actually green on GitHub via `gh run list`, not just locally.
  - **`npm run lint` added 2026-08-01, after being absent since milestone 4.** `eslint-plugin-react`'s `react/prop-types` rule had been enabled the whole time, but no component ever declared PropTypes and CI never ran lint — so it had been failing (45 errors) unnoticed for the project's entire history. Fixed by adding `prop-types` as a real dependency and PropTypes to all 10 components that needed them, plus two smaller unrelated lint errors surfaced once the prop-types noise was gone: `playwright.config.js`'s `process.env.CI` needed a Node-globals override in `eslint.config.js` (config files run under Node, not the browser, so `globals.browser` alone left `process` undefined), and an unescaped apostrophe in `App.jsx`'s "Today's Wellness" heading (`&apos;`). `npm run lint` is now actually clean, not just configured.
